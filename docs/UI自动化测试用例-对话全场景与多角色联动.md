## 0. 代码架构与数据流分析（用例设计依据）

> 以下结论均来自源码阅读，是后续所有断言的「事实基础」。不理解的读者请先读本节。

### 0.1 角色、入口与认证

| 端 | 路由 | 源码 | 访问条件 |
|----|------|------|----------|
| 访客端 | `/chat` | `apps/src/views/chat-widget/index.vue` | `meta.ignoreAccess=true`，**未登录可访问** |
| 座席端 | `/customerservice/agent` | `apps/src/views/customerservice/agent/index.vue` | 需登录；角色 `super_admin` / `kf_manager`（kf_staff 为 403） |
| 员工 AI 对话 | `/customerservice/chat` | `apps/src/views/customerservice/chat/index.vue` | 需登录（本文件不重点覆盖，仅作协议对照） |

### 0.2 通信协议矩阵

| 通道 | 端点 | 用途 | 鉴权 | 源码 |
|------|------|------|------|------|
| AI 对话（SSE） | `POST /api/v1/chat/stream` | 访客→AI 流式回复 | 公开（publicClient） | `useSSEStream.send` |
| 转人工入队 | `POST /api/v1/chat/transfer` | 访客→等待队列 | 公开 | `transferToAgentApi` |
| 身份验证 | `POST /api/v1/chat/auth/sms/send`、`/verify` | 手机号+验证码 | 公开 | `useAuth` |
| 访客 WS | `/ws/chat/{sessionId}` | 接收座席消息 / `AGENT_JOINED` | 公开 | `connectVisitorWs` |
| 座席 SSE | `/api/v1/sessions/events?token=` | 队列事件 ENQUEUE/ACCEPTED/CLOSED/TRANSFER | token(query) | `subscribeSessionEvents` |
| 座席 WS | `/ws/agent/{sessionId}?token=` | 接收访客消息 | token(query) | `connectAgentWs` |
| 座席接入 | `POST /api/v1/sessions/{sid}/accept` | 将会话置为 ACTIVE | token | `acceptSessionApi` |
| 座席结束 | `POST /api/v1/sessions/{sid}/close` | 关闭会话（WS code=1000） | token | `closeSessionApi` |
| 历史消息 | `GET /api/v1/chat/history?sessionId&sinceSeq` | 增量/全量历史 | 访客公开 / 座席 token | `getVisitorHistoryApi` / `getSessionHistoryApi` |
| 等待队列 | `GET /api/v1/sessions/queue` | 座席左侧队列 | token | `getSessionQueueApi` |
| 在线座席 | `GET /api/v1/sessions/agents/online` | 转交 Modal 列表 | token | `getOnlineAgentsApi` |

### 0.3 消息状态真值表（重要：校正原始需求中的「已送达/已读」误解）

> 原始需求把「发送中 / 已送达 / 已读」并列，但经全量代码核查：`WsChatMessage` 协议仅定义 `AGENT_JOINED | CONNECTED | MESSAGE` 三类事件，**无任何 delivered / read 回执**；前端 `Msg` 类型也只有 `sending` 与 `failed` 两个发送态字段。
> 因此本文件以**实测实现**为准：仅「发送中」与「发送失败+重试」是真实状态；「已送达 / 已读」当前版本**未实现**，列为后续增强 gap（见 TC-FLOW-009）。

| 状态 | 触发条件 | UI 表现 | 代码位置 |
|------|----------|---------|----------|
| 发送中 `sending` | 访客 WS 模式发送成功入队 | 用户气泡下方「发送中…」转圈 **250ms 后消失**（无服务端确认） | `chat-widget` `sendWsWithLoading` |
| 发送失败 `failed` | `sendText` 返回 false（WS 未 OPEN）/ WS 异常 | 用户气泡变红 `#fee2e2` + 文字 `#dc2626` + 「重试」按钮 | `useVisitorWs.sendText` |
| AI 流式 `streaming` | SSE 进行中 | 打字光标闪烁 + 思考中三圆点动画 | `useSSEStream.streaming` |
| AI 失败 `failed` | SSE `error` 事件 | 橙底 `#fff7ed` + 「重新生成」按钮 | `onError` |
| 接收（座席） | 访客收到 `MESSAGE role=agent` | 蓝色气泡 `#f0f9ff` + 自动滚底 | `onAgentMessage` |
| 接入通知 | 访客收到 `AGENT_JOINED` | 追加「👤 人工客服已接入，请直接输入您的问题。」 | `onAgentJoined` |
| （缺失）已送达/已读 | —（协议未定义） | 无对应 UI | 断言：当前不存在该状态 |

> 注：座席端 `sendAgent` 为**本地立即回显**消息，窗口不显示「发送中/已送达」；若 WS 未连接，`sendMessage` 返回 false，仅弹 `message.warning('WebSocket 未连接，请重新接入会话')` 且**不**入列。

### 0.4 断线重连策略对照

| 端 / 通道 | 重试上限 | 退避策略 | code=1000 处理 | 增量补齐 | 并发锁 |
|-----------|----------|----------|----------------|----------|--------|
| 访客 WS | 3 次 | `[1000, 3000, 8000]` ms | **不重连**，走 `onSessionClosed` | 按 `localStorage.chat_last_seq_{sid}` 拉增量，仅 `role=agent` | `fetchInflight` 布尔锁 |
| 座席 SSE | 不限 | `min(1000*2^n, 30000)` ms（封顶 30s） | 重新订阅 | 按 `agent_last_seq_{sid}` 拉增量，仅 `role=user` | — |
| 座席 WS | 不限（随 SSE 重连） | 依赖 SSE 重连 + 每会话独立连接 | 由后端语义控制 | 同座席 SSE 机制 | `fetchInflight` 按 sid 的 Set |

### 0.5 会话生命周期状态机

**访客端**
```
idle → AI 对话（SSE）
  →〔点击转人工 / AI 工具触发 transfer〕→ transferred（顶栏「转人工」→「👤 人工服务中」）
  → WS 连接（/ws/chat/{sid}）
  →〔AGENT_JOINED〕→ 对话中
  →〔座席 close，WS code=1000〕→ session_end 分隔条 + sessionEnded=true
  →〔点击「开始新对话」〕→ 新 sessionId（保留旧历史）
```

**座席端**
```
等待队列(WAITING) —SSE ENQUEUE→ 显示「接入会话」
  →〔点击接入 / TRANSFER 自动接入〕→ ACTIVE（加载历史 + WS /ws/agent/{sid}）
  → 对话中（并发 ≤ 5）
  →〔结束会话〕→ CLOSED（断 WS，移出活跃列表）
  →〔转交〕→ TRANSFER SSE → 目标座席自动接入
  →〔并发=5 时接入〕→ 拦截「已达最大并发数（5）」
```

### 0.6 关键存储键

| 键 | 端 | 说明 |
|----|----|------|
| `chat_session_id` | 访客 | 会话 ID，格式 `guest-{Date.now()}-{uuid8}` |
| `chat_history_{sid}` | 访客 | 消息历史，最多 100 条（`slice(-100)`） |
| `chat_last_seq_{sid}` | 访客 | 增量游标（跨标签持久化） |
| `chat_transferred_{sid}` | 访客 | 转接标志（快路径恢复） |
| `agent_last_seq_{sid}` | 座席 | 增量游标 |
| `{NS_PREFIX}-core-access` / `core-access` | 座席 | 登录 token（NS_PREFIX=`vben-web-antd-5.7.0-dev`） |

## 1. 对话功能全场景验证（通信时序 / 消息状态 / 重连 / 历史）

### TC-FLOW-001 访客发起对话 → AI 流式回复（请求-响应时序）
- **测试类型**：正常流程 ｜ **优先级**：P0
- **前置条件**：访问 `/chat`，无历史消息，未转人工。
- **操作步骤**：
  1. 在输入框输入「你们的产品定价是多少？」，按 Enter。
  2. 观察用户气泡与 AI 气泡的先后顺序。
  3. 等待 AI 回复完成（打字光标消失）。
- **预期结果**：用户消息先出现并右对齐；AI 消息随后以流式（逐字）出现；结束后显示完整 Markdown 内容。
- **断言点**：
  - `await expect(page.getByText('你们的产品定价是多少？')).toBeVisible();`（用户消息回显）
  - AI 气泡在用户消息之后出现在 DOM（先 `user` 后 `ai` 顺序）。
  - 流式期间出现打字光标元素（`.animate-pulse` 或思考中三圆点 `.animate-bounce`）。
  - 回复结束后该 AI 消息 `failed` 为 false、存在「复制」图标。

### TC-FLOW-002 消息发送状态机：发送中 → 消失
- **测试类型**：正常流程 ｜ **优先级**：P0
- **前置条件**：访客已转人工且 WS 已连接（顶栏显示「👤 人工服务中」）。
- **操作步骤**：
  1. 输入一条消息并发送（WS 模式）。
  2. 在发送瞬间（<250ms）检查用户气泡下方状态。
  3. 等待 300ms 后再次检查。
- **预期结果**：发送瞬间显示「发送中…」转圈；约 250ms 后该状态消失，消息气泡保留。
- **断言点**：
  - 发送后立即 `await expect(page.getByText('发送中...')).toBeVisible();`（允许短暂存在）。
  - 300ms 后 `await expect(page.getByText('发送中...')).toHaveCount(0);`（已消失）。
  - 用户消息气泡仍然存在（`getByText(发送内容)` 可见）。

### TC-FLOW-003 消息发送失败 → 重试
- **测试类型**：异常流程 ｜ **优先级**：P0
- **前置条件**：访客 WS 处于断开状态（`wsStatus !== 'connected'`，例如断网后重连耗尽或主动断 WS）。
- **操作步骤**：
  1. 在 WS 未连接状态下发送消息。
  2. 检查用户气泡状态。
  3. 点击「重试」按钮（或恢复连接后重试）。
- **预期结果**：`sendText` 返回 false → 气泡变红 + 显示「重试」按钮；点击重试后重新走 WS 发送。
- **断言点**：
  - 用户气泡背景变红（检查内联 style 含 `#fee2e2` 或失败态 class）。
  - `await expect(page.getByRole('button', { name: '重试' })).toBeVisible();`
  - 点击重试后：若 WS 已恢复，气泡「重试」消失、消息正常进入对话；若仍断开，仍为失败态（幂等保护）。

### TC-FLOW-004 WS 异常断线 → 指数退避重连提示
- **测试类型**：异常流程 ｜ **优先级**：P0
- **前置条件**：访客已转人工、WS 已连接，处于对话中。
- **操作步骤**：
  1. 通过 `context.setOffline(true)` 模拟网络断开（触发 WS `onclose` 非 1000）。
  2. 观察消息区提示文案与重连节奏。
  3. 恢复 `context.setOffline(false)`。
- **预期结果**：断线后追加「⚠️ 连接中断，{N}s 后自动重连（{k}/3）…」，延迟依次为 1s → 3s → 8s；网络恢复后重连成功。
- **断言点**：
  - 第一次提示：`getByText(/连接中断，1s 后自动重连（1\/3）/)` 可见。
  - 第二次提示：`getByText(/连接中断，3s 后自动重连（2\/3）/)` 可见（若等待足够久）。
  - 恢复后 `wsStatus` 回到 `connected`，提示不再出现。

### TC-FLOW-005 WS code=1000 正常关闭 → 不重连
- **测试类型**：正常流程 ｜ **优先级**：P0
- **前置条件**：访客对话中，座席侧主动「结束会话」（后端下发 WS code=1000）。
- **操作步骤**：
  1. 座席点击「结束会话」。
  2. 观察访客端是否出现重连提示。
- **预期结果**：访客收到 code=1000 → 走 `onSessionClosed`，**不触发重连**，显示「本次会话已结束」分隔条。
- **断言点**：
  - `await expect(page.getByText('会话已结束')).toBeVisible();`（default 文案「本次会话已结束，感谢您的使用。」子串）
  - 不应出现 `连接中断...自动重连` 文案。
  - 输入区被「开始新对话」按钮替换（见 TC-VIS-007）。

### TC-FLOW-006 重连成功 → 增量补齐座席消息（lastSeq）
- **测试类型**：正常流程 ｜ **优先级**：P0
- **前置条件**：访客已转人工、WS 已连接；座席端在访客断网期间发送了多条消息。
- **操作步骤**：
  1. 访客断网（座席继续发 2 条消息）。
  2. 访客恢复网络，等待重连成功。
  3. 检查访客消息列表是否补齐断网期间的座席消息。
- **预期结果**：重连成功后按 `chat_last_seq_{sid}` 调用 `getVisitorHistoryApi` 补齐，仅渲染 `role=agent` 的消息，避免与 SSE 本地 echo 重复。
- **断言点**：
  - 重连成功后座席断网期间发的消息出现在访客列表。
  - `await page.evaluate(() => Number(localStorage.getItem('chat_last_seq_' + sid)))` 在收到消息后 **> 0** 且单调递增。
  - 补齐消息角色仅为 agent（AI 消息不重复）。

### TC-FLOW-007 历史消息加载（localStorage 恢复，≤100 条）
- **测试类型**：正常流程 ｜ **优先级**：P0
- **前置条件**：访客已有若干条对话记录（未清除）。
- **操作步骤**：
  1. 刷新 `/chat` 页面。
  2. 检查消息区是否恢复历史。
- **预期结果**：从 `chat_history_{sid}` 恢复最近 ≤100 条消息；`msgId` 同步避免 ID 冲突。
- **断言点**：
  - 刷新后历史消息数量与刷新前一致（取前一条消息文本断言可见）。
  - 历史条数 > 100 时仅保留最近 100（见 TC-FLOW-008）。
  - `sessionId` 与刷新前相同（`localStorage.chat_session_id` 不变）。

### TC-FLOW-008 历史消息超 100 条截断
- **测试类型**：边界条件 ｜ **优先级**：P2
- **前置条件**：通过脚本在 `chat_history_{sid}` 写入 120 条消息。
- **操作步骤**：
  1. 刷新 `/chat`。
  2. 检查载入消息条数。
- **预期结果**：仅保留最近 100 条（`msgs.slice(-100)`）。
- **断言点**：
  - 载入后消息总数 = 100（或接近 100，取决于旧数据）。
  - 最早的消息已被丢弃（首页首条文本不再是原第 1 条）。

### TC-FLOW-009 消息「已送达 / 已读」状态缺失断言（Gap 文档化）
- **测试类型**：边界条件（需求校正）｜ **优先级**：P2
- **前置条件**：访客 WS 模式发送消息并被座席接收。
- **操作步骤**：
  1. 发送消息，等待座席端显示。
  2. 检查访客/座席两端是否出现「已送达」「已读」标识或状态变更。
- **预期结果**：当前协议与前端**均无**「已送达 / 已读」状态（见 0.3 节）。
- **断言点**：
  - 访客用户气泡在「发送中」消失后**不再**出现「已送达 / 已读」文案或图标。
  - 座席端收到消息后，访客端**不会**因「已读」产生任何 UI 变更。
  - 备注：建议作为后续增强项（在 `WsChatMessage` 增加 `DELIVERED`/`READ` 事件并在 `Msg` 增加对应字段）。

### TC-FLOW-010 SSE 控制器中断与并发取消
- **测试类型**：异常流程 ｜ **优先级**：P1
- **前置条件**：访客 AI 对话流式进行中（SSE 未结束）。
- **操作步骤**：
  1. 流式进行中再次发送消息（触发 `sse.send` 内 `abortCtrl.abort()`）。
  2. 或关闭页面（`onUnmounted` 调 `sse.abort()`）。
- **预期结果**：`AbortController` 取消上一个未完成请求，防止并发写同一气泡；`AbortError` 不视为业务失败。
- **断言点**：
  - 快速连续发送时仅最后一个 AI 气泡被更新，无重复气泡叠加。
  - 页面卸载不抛未捕获异常（监听 `pageerror` 应为空）。

### TC-VIS-003 输入消息
- **测试类型**：正常流程 ｜ **优先级**：P1

- **操作步骤**：座席 A 打开转交 Modal → 选择座席 B → 确认转交。
- **预期结果**：后端广播 `TRANSFER` SSE（toAgentId=B）；座席 B 自动接入（无需手动 accept）；座席 A 本地移除该会话。
- **断言点**：
  - 座席 B：`getByText(/已自动接入转交会话/)` 可见，且会话出现在「人工接待中」。
  - 座席 A：该会话从列表消失（`getByText(/已成功转交给/)`）。
  - 访客端不感知转交（仍与「人工客服」对话，消息继续可达）。

### TC-DUAL-006 异常：座席离线期间访客发消息 → 座席重连补齐
- **测试类型**：异常流程 ｜ **优先级**：P0
- **前置条件**：双方对话中；座席 SSE/WS 连接正常。
- **操作步骤**：
  1. 座席 `setOffline(true)`。
  2. 访客发送 2 条消息。
  3. 座席 `setOffline(false)`，等待 SSE/WS 重连。
- **预期结果**：座席重连后凭 `agent_last_seq` 补齐断网期间访客消息，无丢失、无重复。
- **断言点**：
  - 重连完成后座席对话区出现访客断网期间的 2 条消息。
  - `agent_last_seq_{sid}` 更新为最新 seq。
  - 访客端不出现重连失败的破坏性提示（仅座席侧重连）。

### TC-DUAL-007 业务标签自动检测同步（退款 → 退款 Tag）
- **测试类型**：正常流程 ｜ **优先级**：P1
- **前置条件**：访客未转人工。
- **操作步骤**：访客发送含「我要退款」的消息后转人工。
- **预期结果**：`detectTag` 推断 tag=「退款」；座席队列卡片 Tag 显示「退款」（橙色）。
- **断言点**：
  - 座席等待队列卡片 `getByText('退款')` 可见（Tag color=orange）。
  - 右侧「转接原因」卡片含「退款」相关原因文本。

### TC-DUAL-008 并发一致性：两侧消息顺序 / 数量一致
- **测试类型**：正常流程 ｜ **优先级**：P1
- **前置条件**：双方对话中，互发多轮。
- **操作步骤**：连续 3 轮「访客→座席→访客→座席」。
- **预期结果**：两侧消息序列（按时间/seq）应完全一致，无乱序、无丢条。
- **断言点**：
  - 访客侧用户消息数 = 座席侧 role=user 消息数。
  - 座席侧 role=agent 消息数 = 访客侧 role=agent 消息数。
  - 任意一轮「访客 X」后紧跟「座席 Y」的顺序在两侧一致。

## 5. 边界与异常场景

### TC-EDGE-001 网络中断恢复（访客端不崩溃）
- **测试类型**：异常流程 ｜ **优先级**：P0
- **前置条件**：访客已转人工、对话中。
- **操作步骤**：`context.setOffline(true)` 3s → `setOffline(false)`。
- **预期结果**：断网期间出现重连提示但不抛错；恢复后 WS 重连，页面仍可继续发送。
- **断言点**：
  - 断网期间 `pageerror` 事件为空（监听收集）。
  - 恢复后输入框仍可发送（`getByRole('textbox', { name: '输入您的问题...' })` 可见且可 fill）。

### TC-EDGE-002 空消息拦截（按钮 disabled / 不发送）
- **测试类型**：边界条件 ｜ **优先级**：P0
- **前置条件**：任意对话态。
- **操作步骤**：
  1. 输入框为空时检查发送按钮状态。
  2. 仅输入空格后尝试发送。
- **预期结果**：空输入时发送按钮 `disabled`；`sendMsg` 内 `if (!text) return` 直接拦截，无空气泡。
- **断言点**：
  - 空输入：`getByRole('button', { name: '发送' })` 的 `disabled` 为 true（或 `button[type=submit]` 禁用）。
  - 全空格输入发送后：消息区不出现空白气泡（`getByText(' ')` 不应作为新消息出现）。

### TC-EDGE-003 超长消息处理（长文本发送与渲染）
- **测试类型**：边界条件 ｜ **优先级**：P1
- **前置条件**：AI 对话态（或转人工后 WS 态）。
- **操作步骤**：构造 5000 字符文本发送。
- **预期结果**：消息被正常发送（代码未做长度截断）；气泡内 `white-space: pre-wrap; overflow-wrap: break-word` 自动换行不溢出；座席/AI 端正常接收渲染。
- **断言点**：
  - 发送后该超长文本气泡可见（不截断为省略号，除非 UI 另有设计）。
  - 消息容器无横向滚动条溢出（气泡宽度受 `max-w-sm` 约束，文本换行）。
  - 接收端完整收到相同文本（长度一致）。

### TC-EDGE-004 快速连续发送（AI 流式期间拦截 / WS 模式）
- **测试类型**：边界条件 ｜ **优先级**：P1
- **前置条件**：AI 对话流式进行中（或 WS 模式）。
- **操作步骤**：
  1. AI 流式回复未结束时快速连发 3 条消息。
  2. WS 模式下快速连发 3 条。
- **预期结果**：
  - AI 模式：`sse.streaming` 期间 `sendMsg` 被 `if (sse.streaming.value) return` 拦截，仅最后一条（流式结束后）可发，无并发气泡错乱。
  - WS 模式：每条各自 `sendText`，可连续发送（受 WS 连接状态约束）。
- **断言点**：
  - AI 模式：流式期间发送按钮 `loading`（`:loading="sse.streaming.value"`），连发不产生 3 个并发 AI 气泡。
  - WS 模式：3 条消息均出现在对话区（无丢失）。

### TC-EDGE-005 WS 未连接时座席发送 → 警告且不推送
- **测试类型**：异常流程 ｜ **优先级**：P1
- **前置条件**：座席已接入会话但 WS 意外断开（如断网）。
- **操作步骤**：在 WS 未连接时点击发送。
- **预期结果**：`sendMessage` 返回 false → 弹 `message.warning('WebSocket 未连接，请重新接入会话')`，且**不**将消息加入本地列表（避免假成功）。
- **断言点**：
  - `getByText('WebSocket 未连接，请重新接入会话')` 可见。
  - 输入文本**未**作为座席气泡出现（不污染对话记录）。
  - 输入框文本被清空（`msgInput.value=''` 在成功分支才执行；失败分支文本保留以便重发——按实际代码，失败分支不 push 也不清空，故断言文本仍在输入框）。

### TC-EDGE-006 重连耗尽 → 提示重连失败 + 清除转接
- **测试类型**：异常流程 ｜ **优先级**：P0
- **前置条件**：访客已转人工、WS 连接；持续断网超过 3 次重连窗口（1+3+8s）。
- **操作步骤**：保持离线 > 12s，然后检查提示。
- **预期结果**：3 次重连均失败后，`onMaxRetryExceeded` 追加「⚠️ 与客服的连接已断开，请重新点击「转人工」或刷新页面。」并清除转接标志。
- **断言点**：
  - `getByText(/与客服的连接已断开/)` 可见。
  - `localStorage` 中 `chat_transferred_{sid}` 被移除（evaluate 返回 null）。
  - 顶栏「👤 人工服务中」恢复为「转人工」按钮。

### TC-EDGE-007 localStorage 超限容错
- **测试类型**：边界条件 ｜ **优先级**：P2
- **前置条件**：人为将 localStorage 填满（逼近配额）。
- **操作步骤**：发送多条消息，触发 `saveHistory` 写入。
- **预期结果**：写入失败时 `catch` 静默忽略（`saveHistory` 空 catch），不影响正常收发。
- **断言点**：
  - 超限环境下发送消息仍成功回显（功能不崩）。
  - 无未捕获异常（`pageerror` 为空）。

### TC-EDGE-008 转人工幂等（重复点击不重复入队）
- **测试类型**：边界条件 ｜ **优先级**：P1
- **前置条件**：访客 AI 对话态，未转人工。
- **操作步骤**：快速连续点击两次「转人工」。
- **预期结果**：`requestTransfer` 内 `if (transferred.value) return true` 幂等保护，仅调用一次 `transferToAgentApi`，不产生重复入队（避免 `SessionEnqueueException`）。
- **断言点**：
  - 座席等待队列该访客仅出现 **1** 次（不重复卡片）。
  - 顶栏仅显示 1 个「👤 人工服务中」徽标。

### TC-EDGE-009 会话恢复（刷新后从 localStorage 恢复转接状态）
- **测试类型**：正常流程 ｜ **优先级**：P0
- **前置条件**：访客已转人工、WS 已连（localStorage 有 `chat_transferred_{sid}`）。
- **操作步骤**：刷新 `/chat` 页面。
- **预期结果**：`onMounted` 调 `restoreTransferState` → 快路径命中 localStorage 标志 → 直接恢复 WS 连接（无新网络请求），顶栏恢复「👤 人工服务中」。
- **断言点**：
  - 刷新后顶栏仍为「👤 人工服务中」（未退回「转人工」）。
  - WS 重新连接（`/ws/chat/{sid}` 重建），可继续收发。
  - 无重复 `transferToAgentApi` 调用（仅恢复 WS）。

### TC-EDGE-010 验证码错误 / 手机号格式校验
- **测试类型**：异常流程 ｜ **优先级**：P1
- **前置条件**：访客触发身份验证 Modal（敏感词或点身份徽标）。
- **操作步骤**：
  1. 手机号输入 `123`（非法）→ 点发送验证码。
  2. 合法手机号发码后，验证码输入 `000000`（无效）→ 点立即验证。
- **预期结果**：手机号正则 `^1[3-9]\d{9}$` 校验失败提示；验证码错误提示「验证码错误，请重试」并清空。
- **断言点**：
  - 非法手机号：`getByText('请输入正确的手机号')` 可见，且未真正发码（无倒计时）。
  - 错误验证码：`getByText('验证码错误，请重试')` 可见；验证码输入框被清空。

| 模块 | 用例数 | P0 | P1 | P2 | 覆盖类型 |
|------|--------|----|----|-----|----------|
| 1. 全场景验证（时序/状态/重连/历史） | 10 | 8 | 1 | 1 | 正常+异常+边界 |
| 2. 访客页面 `/chat` | 11 | 9 | 2 | 0 | 正常为主 |
| 3. 客服页面 `/customerservice/agent` | 14 | 10 | 4 | 0 | 正常+边界 |
| 4. 多角色联动 | 8 | 7 | 1 | 0 | 正常+异常 |
| 5. 边界与异常 | 10 | 6 | 3 | 1 | 异常+边界 |
| **合计** | **53** | **40** | **11** | **2** | — |

**覆盖核对（对应增强需求 5 要点）**
- 对话功能全场景：TC-FLOW-001~010（时序、状态、断线重连、历史加载全覆盖）
- 访客页面：TC-VIS-001~011（开窗口、输入、发送、收回复、关闭对话）
- 客服页面：TC-WB-001~014（登录、接访列表、对话切换、回复、结束）
- 多角色联动：TC-DUAL-001~008（双向实时、状态同步、多会话并发、转交）
- 边界异常：TC-EDGE-001~010（断网恢复、空消息、超长、快速连发等）

**需重点说明的偏差**
1. 原始需求把「发送中/已送达/已读」并列，但代码仅实现「发送中」与「发送失败+重试」；「已送达/已读」当前未实现（TC-FLOW-009 已文档化为 gap）。
2. 座席端发送为本地回显，无逐消息「发送中/已送达」状态；WS 未连时仅告警不推送（TC-EDGE-005）。
3. 转人工「已为您转接人工客服」文案来自员工 AI 对话页（`/customerservice/chat`）与 `useSSEStream` 默认 transfer 载荷；访客 widget 的确定性信号是顶栏「👤 人工服务中」徽标与「人工客服已接入」消息，用例以此为准。

## 7. 运行与维护建议

- **单角色用例**可直接套用 `apps/tests/e2e/fixtures.ts` 的 `cleanStorage` / `superAdminLogin`。
- **多角色用例**建议复用 `agent-session.spec.ts` 的 `apiLogin` + `injectTokenCtx` 范式，避免座席端登录页时序抖动；访客端保持真实 UI 操作。
- **断网/重连类**用例用 `context.setOffline(true/false)`，并注意真实重连延迟（访客 1/3/8s，座席 SSE 封顶 30s），适当放宽 `expect` 超时。
- **增量补齐类**用例断言 `localStorage` 中的 `chat_last_seq_*` / `agent_last_seq_*` 单调更新，比单纯数消息更稳健。
- 本文件与 `docs/UI自动化测试用例.md`（全模块 426 条）互补：非对话类模块以主文档为准，对话类深度场景以本文件为准。
