# 座席工作台功能缺口分析报告

> 文档版本：v1.0  
> 分析日期：2026-07-08  
> 分析范围：`apps/src/views/customerservice/agent/index.vue` 及相关 composables / API 层  

---

## 一、概述与背景

### 1.1 页面定位

座席工作台（Agent Workbench）是 AI 智能客服系统的核心操作界面，承载以下核心职责：

- 座席在线状态管理（上线 / 下线切换）
- 等待队列的实时监控与接入
- 多会话并发处理（最多 5 个并发，`MAX_CONCURRENT = 5`）
- 与访客的实时消息收发（基于 WebSocket）
- AI 对话上下文的查看与人工介入
- 会话结束、转交等生命周期操作

### 1.2 技术架构现状

| 层次 | 实现方式 |
|---|---|
| 实时消息 | WebSocket（`useAgentWebSocket`），每个 session 独立连接 |
| 队列推送 | SSE（`useSessionQueue`），带指数退避重连，最大间隔 30s |
| 状态管理 | 组件内 `ref` / `reactive`，无全局 store |
| API 通信 | REST，基于 axios，token 通过 Header 传递 |
| 测试覆盖 | Playwright E2E 4 个用例；无 composable 单元测试 |

### 1.3 分析方法

本报告通过以下方式识别功能缺口：

1. 截图走查：对照页面截图与真实客服工作台 UX 标准逐项比对
2. 代码审查：阅读组件、composables、API 层，核查逻辑完整性
3. 测试覆盖审查：梳理已有测试用例，识别未覆盖的关键场景
4. 行业对标：参照主流客服系统（Zendesk、Intercom、阿里云客服）的标准功能集

缺口按**产品功能**和**测试覆盖**两个维度分类，优先级分为高 / 中 / 低三档。

## 二、产品视角 — 高优先级功能缺口

> 高优先级：直接影响核心工作流正确性或数据一致性，建议在下一个迭代内修复。

---

### P1-1 座席在线状态未同步后端

**现象**  
组件内 `agentOnline` 是纯前端 `ref<boolean>`，切换时不调用任何 API。

**影响**  
- 座席刷新页面或关闭浏览器，服务端仍认为其在线，持续向其推送会话
- 多座席负载均衡分配错误，访客可能长时间等待一个"幽灵在线"座席
- 运营管理后台看到的在线座席数不准确

**建议修复**  
1. 新增 `PUT /api/v1/agent/status { status: 'ONLINE' | 'OFFLINE' | 'BUSY' }` 接口
2. `agentOnline` 切换时调用该接口，失败则回滚 UI 并提示
3. 页面 `beforeUnload` / `visibilitychange` 时自动发送下线请求（或依赖心跳超时检测）

---

### P1-2 快捷回复硬编码，无法配置

**现象**  
截图底部的「已核实订单信息」「安排补发处理」「提交快递投诉」「退款申请处理」「感谢您的耐心等待」是组件内写死的字符串数组，无法通过管理界面维护。

**影响**  
- 业务场景变化时需发版才能更新话术
- 不同业务线/部门无法使用各自的快捷话术
- 无法按场景分组（订单类、物流类、退款类等）

**建议修复**  
1. 后端新增快捷回复库接口 `GET /api/v1/quick-replies?category=&keyword=`
2. 管理端新增「快捷回复」配置页面，支持分组和排序
3. 前端改为动态加载，支持关键词本地过滤
4. 支持个人常用 + 团队共享两个维度

---

### P1-3 输入框功能单薄

**现象**  
输入区域只有一个纯文本 `textarea` + 发送按钮，无任何富文本能力。

**缺失功能清单**

| 功能 | 现状 | 影响 |
|---|---|---|
| 图片/截图粘贴上传 | ❌ 缺失 | 无法直接发操作截图给访客 |
| 文件附件 | ❌ 缺失 | 无法发票据、说明书等文件 |
| 表情符号 | ❌ 缺失 | 表达受限 |
| 字数限制提示 | ❌ 缺失 | 超长消息体验差 |
| Enter/Shift+Enter 说明 | ❌ 缺失 | 新用户困惑发送方式 |
| 草稿自动保存 | ❌ 缺失 | 切换会话时输入内容丢失 |

**建议修复优先级**：草稿保存 > Enter 快捷键说明 > 图片粘贴 > 文件上传 > 表情

---

### P1-4 多会话新消息无通知机制

**现象**  
当座席正在处理会话 A 时，会话 B 新来消息，仅靠左侧队列列表的绿色圆点变化提示，无其他感知手段。

**影响**  
- 座席专注于当前会话时极易漏看其他会话的新消息
- 等待回复的访客体验恶化，CSAT 下降
- 违反大多数客服系统的 "首响时间" SLA 约定

**建议修复**  
1. 浏览器桌面通知（`Notification API`），需用户授权
2. 标签页 favicon 动态 badge（未读会话数）
3. 页面内 toast 提示（不打断当前操作）
4. 可选音效提醒（用户可在个人设置中关闭）
5. 左侧队列列表中的未读消息数角标

## 三、产品视角 — 中优先级功能缺口

> 中优先级：影响座席工作效率和访客体验，建议在 1-2 个迭代内跟进。

---

### P2-1 无访客打字状态提示

**现象**  
聊天区域无"访客正在输入..."的指示器。

**影响**  
- 座席不知道访客是否在输入中，容易发出打断性回复
- 对话节奏感差，显得系统"无响应"

**建议修复**  
后端通过 WebSocket 推送 `TYPING` 事件，前端在消息区底部展示「访客正在输入...」气泡，3 秒无更新后自动消失。

---

### P2-2 会话内无消息搜索

**现象**  
中间消息区只有「全部 / AI对话 / 人工回复」三个 tab 过滤，无关键词搜索。

**影响**  
- 长会话（几十轮）中无法快速定位历史消息
- 座席向访客确认信息时需手动翻找

**建议修复**  
消息区顶部新增搜索入口，高亮匹配关键词，支持 ↑↓ 导航。不需要后端支持，纯前端基于 `msgs` 数组过滤即可。

---

### P2-3 无内部备注功能

**现象**  
座席无法在会话中添加对访客不可见的内部备注。

**影响**  
- 座席无法记录处理进展（如"已联系仓库，等待反馈"）
- 转交时接手方缺乏上下文，需重新询问访客
- 会话结束后无法给复盘留下线索

**建议修复**  
1. 输入框区域新增「备注」入口，发送的备注消息以不同样式展示（如灰色斜体背景），前端标记 `role: 'note'`
2. 后端存储时标记为内部消息，不下发给访客端
3. 转交时备注随会话历史一并传递

---

### P2-4 转交缺少交接备注字段

**现象**  
转交弹窗只显示在线座席列表和确认按钮，`transferSessionApi` 只传 `{ targetAgentId }`，无备注字段。

**影响**  
接手座席只能看到原始转接原因（"用户主动请求转人工"），无法了解当前问题进展，需重新询问访客。

**建议修复**  
转交弹窗新增「交接备注」文本框，内容通过 `{ targetAgentId, note: string }` 随转交请求传递，在接手座席侧的转换原因区域展示。

---

### P2-5 无会话时长显示

**现象**  
右侧面板显示「排队时长」（访客等待被接入的时间），但接入后无「会话时长」计时器。

**影响**  
- 座席无法直观感知当前会话已持续多久
- SLA 监控（如"超过 10 分钟未解决需升级"）无前端依据

**建议修复**  
`SessionData` 增加 `acceptedAt: number` 字段，右侧面板在「排队时长」下方新增「会话时长」实时计时器，逻辑复用 `formatWaitTime` 工具函数。

---

### P2-6 结束会话无满意度收集和解决状态标注

**现象**  
点击「结束会话」 → 确认弹窗 → 直接关闭，无任何后续动作。

**缺失环节**

| 环节 | 现状 | 影响 |
|---|---|---|
| 客户满意度（CSAT）评分触发 | ❌ | 无法度量服务质量 |
| 问题解决状态标注 | ❌ | 无法区分"已解决"和"未解决转单" |
| 结束原因选择 | ❌ | 数据分析维度缺失 |

**建议修复**  
结束会话弹窗新增「问题解决状态」单选（已解决 / 未解决 / 转单跟进），确认后向访客端推送满意度评分邀请；同时将状态随 `closeSessionApi` 一并提交。

---

### P2-7 MAX_CONCURRENT 硬编码

**现象**  
`const MAX_CONCURRENT = 5` 在组件顶部写死，未从配置或用户信息接口读取。

**影响**  
- 不同客户/租户可能有不同并发上限需求
- 超出限制时 UI 无明确提示，只是静默阻止接入
- 无法通过管理后台动态调整

**建议修复**  
后端在用户 profile 接口中返回 `maxConcurrent` 字段，前端 onMounted 时读取并替换硬编码值；同时在达到上限时显示明确的 toast 提示。

---

### P2-8 座席下线时等待访客无提示

**现象**  
座席切换为「下线」状态时，等待队列中的访客不会收到任何通知，仍停留在等待界面。

**影响**  
- 访客无法感知自己在等一个已下线的座席
- 如果分配策略未及时重新路由，访客会无限等待

**建议修复**  
下线时后端触发重新路由逻辑（非前端职责）；前端下线切换时弹出确认框，提示"当前有 N 个等待中的会话，下线后将重新分配"，需用户二次确认。

---

### P2-9 AI 辅助回复建议未集成

**现象**  
页面已展示 AI 对话上下文，但没有「AI 建议回复 → 一键采用」的辅助入口。

**影响**  
AI 上下文的价值停留在"可查看"，未进入"可辅助操作"阶段，座席仍需完全手动输入。

**建议修复**  
在消息区底部（输入框上方）展示 AI 实时建议回复气泡（可折叠），座席点击后填入输入框，可二次编辑再发送。建议建立独立的 SSE 流用于推送 AI 建议，不与主聊天流混用。

---

### P2-10 访客信息维度不足

**现象**  
右侧「会话信息」面板只展示：访客姓名、会话编号、问题标签、排队时长、消息轮数、接入状态。

**缺失信息**

| 字段 | 重要性 | 说明 |
|---|---|---|
| 历史会话入口 | 高 | 该访客之前找过几次，解决了什么问题 |
| 来源渠道 | 高 | 来自网页/App/微信等哪个入口 |
| 当前访客所在页面 URL | 中 | 有助于快速定位问题场景 |
| 设备/浏览器 | 低 | 辅助排查技术问题 |
| 地区信息 | 低 | 辅助判断物流/时区问题 |

## 四、产品视角 — 低优先级功能缺口

> 低优先级：锦上添花，对效率有正向影响，可在产品路线图中按需排期。

---

### P3-1 会话队列无优先级标记

**现象**  
等待队列按先进先出顺序展示，座席无法手动标记某个会话为优先处理（如 VIP 客户、紧急投诉）。

**建议修复**  
支持右键或长按会话项，可标星/置顶；或由后端在 `SessionQueueItem` 中返回 `priority` 字段，前端按优先级排序展示。

---

### P3-2 无键盘快捷键支持

**现象**  
所有操作均需鼠标点击，无法通过键盘完成切换会话、发送消息、接入队列等高频操作。

**缺失快捷键建议**

| 操作 | 建议快捷键 |
|---|---|
| 切换到下一个会话 | `Alt + →` |
| 切换到上一个会话 | `Alt + ←` |
| 接入第一个等待会话 | `Alt + A` |
| 发送消息 | `Enter`（已存在但未标注） |
| 结束当前会话 | `Alt + E`（需二次确认） |

---

### P3-3 工具调用展开状态不持久化

**现象**  
`toolExpanded` 是 `ref<Record<number, boolean>>`，仅存于内存。切换会话或刷新页面后，所有工具调用卡片恢复折叠状态。

**影响**  
查看复杂工具链时需反复展开，对排查长会话问题的效率有轻微影响。

**建议修复**  
将 `toolExpanded` 持久化到 `sessionStorage`，以 `sessionId + msgIndex` 为 key，页面重载后恢复展开状态。

---

### P3-4 已结束会话列表缺少翻页控件

**现象**  
代码中 `getClosedSessionsApi` 支持分页参数，但左侧「已结束」tab 没有翻页按钮或无限滚动加载，只展示首页数据。

**影响**  
座席无法查看超过首页数量的历史会话，审计和复盘场景受限。

**建议修复**  
「已结束」列表底部添加「加载更多」按钮，或改为无限滚动，调用 `getClosedSessionsApi` 的 `page` 参数分批加载。

---

### P3-5 无个人工作数据看板

**现象**  
座席工作台内没有任何数据摘要，座席不知道自己今天处理了多少会话、平均响应时间、满意度评分等。

**建议修复**  
在左侧座席状态区域下方增加简单的今日数据摘要卡片：今日接待数 / 平均首响 / 好评率，数据来自独立的 `GET /api/v1/agent/stats/today` 接口。

---

### P3-6 无会话标签编辑能力

**现象**  
右侧面板展示「问题标签」（如"咨询"），但座席无法在接待过程中修改或追加标签。

**影响**  
AI 自动打标不一定准确，人工更正需依赖其他流程，数据质量受影响。

**建议修复**  
标签区域支持点击编辑，从预设标签列表中选择，调用 `PATCH /api/v1/sessions/:id/tag` 接口实时更新。

## 五、测试视角 — 单元测试缺失

> 当前项目中 `useSessionQueue` 和 `useAgentWebSocket` 两个核心 composable 均无单元测试，这两个模块承载了实时通信和队列管理的核心逻辑，是风险最高的无测试区域。

---

### T1-1 `useSessionQueue` — 无任何单元测试

**文件路径**  
`apps/src/composables/useSessionQueue.ts`

**应覆盖的测试场景**

| 测试用例 ID | 场景描述 | 验证点 |
|---|---|---|
| `SQ-001` | SSE 连接成功后 queue 正确填充 | `queue.value` 包含正确的 `SessionQueueItem` |
| `SQ-002` | 收到 `ENQUEUE` 事件后 queue 新增条目 | 新条目出现在队列末尾 |
| `SQ-003` | 收到 `ACCEPTED` 事件后对应条目从 queue 移除 | queue 长度减 1，对应 sessionId 不存在 |
| `SQ-004` | 收到 `CLOSED` 事件后对应条目状态更新 | 条目 status 变为 `CLOSED` |
| `SQ-005` | SSE 断线后触发重连，间隔符合指数退避规律 | 第 1 次重连 ~1s，第 2 次 ~2s，以此类推，最大 30s |
| `SQ-006` | `waitMin` 计时器每秒更新 queue 中所有条目 | 1 秒后 `waitMin` 字段递增 |
| `SQ-007` | `acceptItem` 调用后 sessionId 对应条目从 queue 移除 | 调用 `acceptSessionApi` 且 queue 中不再含该 id |
| `SQ-008` | `queueSearch` 过滤正确匹配姓名、标签、会话编号 | 过滤结果仅含匹配项 |
| `SQ-009` | 组件卸载后 SSE 连接被正确关闭 | `EventSource.close` 被调用 |

**纯函数单测（独立优先级高）**

```ts
// resolveTagColor
it('应为已知标签返回对应颜色', () => {
  expect(resolveTagColor('咨询')).toBe('blue')
})
it('未知标签应返回默认颜色', () => {
  expect(resolveTagColor('未知标签')).toBe('default')
})

// formatWaitTime
it('206 秒应返回 "3:26"', () => {
  expect(formatWaitTime(Date.now() / 1000 - 206)).toBe('3:26')
})
it('刚入队（0 秒）应返回 "0:00"', () => {
  expect(formatWaitTime(Date.now() / 1000)).toBe('0:00')
})
```

---

### T1-2 `useAgentWebSocket` — 无任何单元测试

**文件路径**  
`apps/src/composables/useAgentWebSocket.ts`

**应覆盖的测试场景**

| 测试用例 ID | 场景描述 | 验证点 |
|---|---|---|
| `WS-001` | `connectSession` 后 statusMap 变为 `CONNECTING` | `statusMap[id]` 值正确 |
| `WS-002` | WS `onopen` 后 statusMap 变为 `CONNECTED` | `statusMap[id] === 'CONNECTED'` |
| `WS-003` | WS `onclose` 后 statusMap 变为 `DISCONNECTED` | `statusMap[id] === 'DISCONNECTED'` |
| `WS-004` | `sendMessage` 在 CONNECTED 时正确调用 `ws.send` | `ws.send` 被以正确 JSON 调用 |
| `WS-005` | `sendMessage` 在非 CONNECTED 时抛出或静默失败 | 不调用 `ws.send`，无异常泄漏 |
| `WS-006` | `disconnectSession` 调用 `ws.close` 并清理 Map | Map 中不再含该 sessionId |
| `WS-007` | `onReconnect` 在 WS open 时被调用 | 回调被执行一次 |
| `WS-008` | 并发 5 个 session 的 statusMap 互不干扰 | 每个 id 对应各自独立的状态 |
| `WS-009` | 重复调用 `connectSession` 同一 id 不创建多余连接 | Map 中仍只有一个该 id 的连接 |

### T1-3 测试基础设施建议

当前项目已有 Vitest 配置（`useSSEStream.test.ts` 证明），可直接在同目录新增测试文件，无需额外配置。

## 六、测试视角 — E2E 覆盖盲区

> 当前已有 E2E 用例：TC-WB-SEARCH（队列搜索）、TC-WB-CTX（右侧面板数据）、TC-WB-CLOSE-01（结束会话弹窗）、TC-WB-CONN-03（WS 状态点）。以下为尚未覆盖的关键场景。

### T2-1 达到 MAX_CONCURRENT 时的接入行为

### 8.3 关键决策点

在推进以上改进时，以下几点需产品和技术提前对齐：

1. **AI 建议回复的触发时机**：是实时流式推送（独立 SSE），还是座席点击后请求？实时流式体验好但成本高。

2. **快捷回复的权限边界**：个人快捷回复 vs 团队共享 vs 管理员统一配置，三者的边界和优先级需明确。

3. **内部备注的存储策略**：备注是否计入消息轮数？是否在分析报表中展示？需与数据团队对齐。

4. **满意度评分的触发方**：由前端在结束会话时主动推送，还是由后端监听 `CLOSED` 事件统一触发？建议后端统一触发，避免前端多端不一致。

5. **XSS 防御审计**：需要 review 组件中所有 `v-html` 的使用点，优先级高于功能迭代。
